- `storeBlob` now writes each blob whole to a staging file in `blobs/`, syncs it, and renames it to the blob's own name. On Unix it then syncs the directory naming the blob, and `blobs/` too when the blob starts a new shard directory, where the system syncs directories and the account may open them. A store cut short used to leave a truncated file under the blob's name, which `getBlob` couldn't read. Opening a store removes the staging files (`.chronicle-blob-*`) that stores killed before their rename left in `blobs/`.
- `storeBlob` of bytes whose stored file can't be read back as those bytes, such as one a cut-short store left, now replaces that file. It used to keep the file and return the hash, so the blob stayed unreadable. To tell, a store of bytes that aren't in the cache now reads their stored file once, where it used to check only that a file was there. An error that keeps the file from being read at all, such as a permission error, now fails the store, as it fails `getBlob`. A store of cached bytes whose file has gone writes the file again.
- `getBlob` of a file whose header names more content than the file holds now fails with an error naming the file. It used to allocate the length the header named, which for `u64::MAX` panicked.
- `storeBlob` refuses a content type longer than 65,535 bytes. It used to write the type's length cut to 16 bits and return the hash, and a later `getBlob` of that blob read a length from the type's own bytes, which for a type of 65,536 `t`s aborted the process.
