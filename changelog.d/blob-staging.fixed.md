- `storeBlob` now writes each blob whole to a staging file in `blobs/`, syncs it, and renames it to the blob's own name. On Unix, before it returns, the directories holding the blob's name have been synced since this open store last made or renamed anything into them, where the system syncs directories and the account may open them; what an earlier process or an earlier open of the store made is taken as it is. A store cut short used to leave a truncated file under the blob's name, which `getBlob` couldn't read. Opening a store removes the staging files (`.chronicle-blob-*`) that stores killed before their rename left in `blobs/`, where it can list `blobs/`.
- `storeBlob` of bytes whose stored file is cut short, damaged or holds other bytes now replaces that file. It used to keep the file and return the hash, so the blob stayed unreadable. To tell, a store of bytes that aren't in the cache now reads their stored file once, where it used to check only that a file was there. Something other than a regular file at the blob's name or a link's target, or a file that can't be opened or read, such as for its permissions, now fails the store and is left as it is. A store of cached bytes whose file has gone writes the file again. A symbolic link at a blob's name is read through: one whose target reads back as the bytes is left, and one whose target is cut short, damaged, holds other bytes or doesn't exist is itself replaced by the blob, leaving any target as it was; one that loops fails the store.
- `getBlob` of a file cut short, or whose header names more content than the file holds, now fails with an error that names the file and says storing the same bytes again replaces it. A cut-short file used to fail with `failed to fill whole buffer`, and a header naming `u64::MAX` bytes made `getBlob` panic. A blob whose bytes are cached is still answered from memory.
- `storeBlob` refuses a content type longer than 65,535 bytes. It used to write the type's length cut to 16 bits and return the hash, and a later `getBlob` of that blob read a length from the type's own bytes, which for a type of 65,536 `t`s aborted the process. Such a blob written before this release now fails `getBlob` with an error instead.
