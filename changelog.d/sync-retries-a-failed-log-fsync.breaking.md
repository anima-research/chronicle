- **Callers that write after a failed log fsync:** such a write now first writes the records since the last good fsync again, from memory, and fsyncs. When that retry succeeds, the write goes on, and the caller doesn't see the failure. This covers every append, state write, field-index registration and metadata call, but not a blob write. Such a write throws `DurabilityLost` while the retry still fails, and then it changes nothing. A metadata call can also throw it when its own checkpoint fails at the fsync of the log, and then it undoes its change. Before, such writes went on with no retry, and `sync()` threw `DurabilityLost` until the store was reopened.
  - **What ends it:** the failure ends when a retry's fsync succeeds. Reopening the store also ends the failure. Each of these calls makes the retry, and it can now succeed where it threw before:
    - each write named above;
    - `sync()` and `close()`;
    - a dropped Rust `Store`.
  - **Migration:** when a write throws `DurabilityLost`, make it again later. The open store holds what it held before the write, with the one exception that the entry on failed metadata calls names. Each later write and `sync()` tries the retry again. While the disk keeps failing, each retry writes up to 64 MiB and one record again and waits for the disk, and reads wait for it too. After `close()` throws `DurabilityLost`, reopen the store to see what it holds. A caller that reopens the store on `DurabilityLost` needs no change.
  - **Unchanged:** the on-disk format is the same, so existing stores open as before. An append still returns its record when its own periodic fsync fails, and the error is still `DurabilityLost`.
- **Callers that open a store:** an open now fsyncs the record log first, and throws `DurabilityLost` when that fsync fails. In that case, records written before the open may not be on the disk. A later open doesn't report the failure again.
