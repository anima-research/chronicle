- `Store::create` (and `JsStore.create`) on a directory that already holds a store no longer resets it. It used to keep the records but publish empty state and branch indexes over the store's own at the first sync, losing every registration and branch with no error. It now refuses with `InvalidOperation`, naming the path, both for a store and for a damaged one (a `MANIFEST` that doesn't verify, or a link with nothing behind it; its `records.log`, `state.bin`, `state-indexes.bin` or `branches.bin` without a `MANIFEST`; or a `blobs/` directory with data in it without one). `create`, asked for by name, still takes a `blobs` link; `open_or_create` refuses one. It also takes the store's lock before writing anything, so a create aimed at a store another process has open no longer rewrites that store's `MANIFEST` before failing with `Locked`, and it writes `MANIFEST` atomically, so a crash can't leave one cut short (#34).
- `Store::open_or_create` on a directory without a `MANIFEST` that holds nothing but `lost+found` (a fresh volume's root), Finder's `.DS_Store`, or what a create leaves when it stops before its manifest (`LOCK`, an empty `blobs/`, and beside that `LOCK` the staging file of its manifest save) now creates the store there (with `create_if_missing`), instead of failing to open it. When another create finishes and closes between its look and its lock, it opens that store; one still open is `Locked` (#34).
