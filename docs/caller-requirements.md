# What chronicle's callers require of the store

Three programs call chronicle's store: agent-framework, context-manager and connectome-host. This file lists what their calls rely on, one requirement for each line, by the method of `JsStore`. It has 668 requirements of 54 methods.

**How the list was made.** For each method, a reader read the three callers' code outside their tests and wrote down each thing that a call relies on. 27 more requirements were found in tests of the store itself, and each of those says so. The sentences are the readers' own.

**What a line holds.** A label such as `getStateJson.3`, a status, the requirement's sentence, and the number of calling functions that rely on it. A line with the status not met ends with the case in which today's store behaves differently.

**What a status means.** A second reader, who changed no test, read the tests at the commit `b59a5be` on November 21, 2026 and said for each requirement what the tests show:

- **pinned**: a test fails if the store stops meeting the requirement. There are 625.
- **pinned partly**: a test fails if the store stops meeting a part of the requirement. There are 12.
- **no test**: no test fails. There are 0.
- **not met**: today's store does not do what the requirement asks, in whole or in part. A test that is marked todo asserts the missing part, or an active test asserts what the store does instead. There are 31.

A status is that reader's finding at that commit. The test suite does not check it, and a later change to the tests can make it stale.

**Todo tests.** Some tests of the suite are marked todo. Each of them asserts something that the store does not do today. The readers had the list of those tests, and a requirement that one of them bears on has the status not met. `npm test` lists the todo tests.

## `appendJson`

- `appendJson.1` — **pinned** — Each successful call adds one new record under the exact type string supplied, without replacing older records of that type. The types distinguish entries from checkpoints and store identity from accepted layouts. (3 calling functions)
- `appendJson.2` — **pinned** — The caller passes a JavaScript value, not pre-encoded bytes. Reading the appended record with `getRecord(id)` must yield a payload that decodes as UTF-8 JSON to that value, including nested entries, snapshots, layout deltas and receipts. (3 calling functions)
- `appendJson.3` — **pinned** — On normal return, the append has taken effect synchronously: the record is listed by `getRecordIdsByType(type)` and readable by ID on the current store object. Even if handling the result or a subsequent `sync()` fails, replay can find the record without reopening; this also lets an identity retry reuse the UUID it already wrote. (3 calling functions)
- `appendJson.4` — **pinned** — Typed records remain discoverable store-wide across historical rollback, branch switches, branch deletion and reopen. In particular, a fold receipt can name the branch it was compiled on without switching back to that branch to append it. (3 calling functions)
- `appendJson.5` — **pinned** — A typed append takes the next record sequence on the branch selected at write time, in the same sequence space as that branch's messages. This is separate from both the global ID and any branch named inside the payload. (3 calling functions)
- `appendJson.6` — **not met** — A successful `store.sync()` after the append must make that record and preceding appends durable; the append result alone need not establish this. The callers use this barrier before acting on a durable journal entry, caching or returning a minted identity, or announcing acceptance. (3 calling functions) Not met: After an append in a newly created store, sync flushes the log but not the parent directory entry for the store, so power loss can make even the synced record unreachable.
- `appendJson.7` — **pinned** — An append failure must throw during the call, not silently return a sentinel or reject a promise later. The identity writer then exits before caching the mint, and the two journal writers distinguish failure from a successful write before they report it. (3 calling functions)
- `appendJson.8` — **pinned** — The synchronous result must expose `.id`, the same ID used by type enumeration and `getRecord`. That ID must continue to name the retained record: later checkpoint boundaries, delta and receipt links, compile marks and receipt cursors use it; the fold journal explicitly tolerates reissue if open drops a rotten last record. (2 calling functions)
- `appendJson.9` — **pinned** — IDs must be positive decimal strings, unique and strictly increasing in store-wide append order, not branch-local sequences or per-type counters. The journals compare them numerically and use zero as the boundary before the first entry. (2 calling functions)
- `appendJson.10` — **not met** — A successful `store.sync()` before the append must order the referenced state onto stable storage first. An entry asserting that state, or a layout naming messages and summaries, must not survive without it. (2 calling functions) Not met: For a newly created store, sync can return before the journal append without syncing the parent directory entry needed to find the referenced state after power loss.
- `appendJson.11` — **pinned** — An accepted layout and its optional receipt must land as one commit: a crash or failed append must not publish one part without the other. (1 calling function)
- `appendJson.12` — **pinned partly** — Appending an accepted-layout record must extend that type's ID list at the end, preserving its previous prefix in ascending order. The fold index pushes successful IDs itself, refreshes from its previous length after failure, and needs the IDs it compares to remain distinguishable in order when converted to JavaScript `Number`. (1 calling function)
- `appendJson.13` — **pinned** — `RecordJournal.write` also requires the result's `.sequence` to be the numeric branch sequence of the appended record, consistent with the sequence later read during replay. (1 calling function)
- `appendJson.14` — **pinned** — For a plain journal append, the record must reach the OS before return and survive a killed writer process without requiring the caller to sync. This is not a promise of stable storage after power loss. (1 calling function)
- `appendJson.15` — **pinned** — If the append itself throws, `RecordJournal` does not require rollback or trust the current index to show whether the write landed. It stops further writes, and requires a reopened store to expose any intact record left in the log so it is reduced before later checkpoints. (1 calling function)
- `appendJson.16` — **pinned partly** — For a fold acceptance retried on the same store after an append throws, any acceptance that actually landed must be discoverable on the next type-list refresh with its original compile ID and receipt. Otherwise the caller's retry can write a second acceptance instead of returning the first. (1 calling function)
- `appendJson.17` — **pinned** — For workspace callers to identify the OS cause of a journal append failure, the thrown value must expose a recognizable errno code, or on POSIX be an `Error` whose message matches `IO error: … (os error N)`. A particular generic error code is not required; other forms lose the errno-specific explanation. (1 calling function)
- `appendJson.18` — **pinned** — The generic typed writer refuses the reserved `state_update` type before recording anything or advancing the branch. A caller-chosen journal type and payload cannot become a named-state mutation on replay. (found in a test of the store)
- `appendJson.19` — **pinned** — Appending bounded-size typed records has bounded amortized disk cost: the store footprint grows with the records added, not with repeated copies of the accumulated journal. (found in a test of the store)

## `appendManyToStateJsonWithIdentity`

- `appendManyToStateJsonWithIdentity.1` — **pinned** — The store handle exposes a function named `appendManyToStateJsonWithIdentity` even before the first window write. Context-manager and agent-framework check the handle at open or creation; context-manager checks again before registering the state for a multi-item write, with no per-item fallback. (2 calling functions)
- `appendManyToStateJsonWithIdentity.2` — **pinned** — It accepts the window's registered append-log state ID, an array of ordinary JavaScript objects, `'by'` as the ID field and `'at'` as the sequence field, in that order. The objects are payloads, not references the store must resolve: the reload benchmark appends `{id}` objects for which no message was stored. (2 calling functions)
- `appendManyToStateJsonWithIdentity.3` — **pinned** — It extends the existing list without changing its prefix, placing each input object at the next consecutive item ordinal in input order, not nesting the array at one ordinal. Single-item and batched appends use the same list; headers and tombstones consume positions just as presentations do. (2 calling functions)
- `appendManyToStateJsonWithIdentity.4` — **pinned** — One invocation writes one record at one sequence, not one record per item. Window write-downs, presentations and retractions rely on this unit of writing, and the reload benchmark seeds its index in records of up to 50 items. (2 calling functions)
- `appendManyToStateJsonWithIdentity.5` — **pinned** — Every stored item carries `by` as the string ID and `at` as the numeric sequence of the record that wrote the batch. These stamps are shared by all items in that write and are distinct from a presented row's own `id` and sequence. (2 calling functions)
- `appendManyToStateJsonWithIdentity.6` — **pinned** — The append completes synchronously on the handle's current branch. By normal return the state's revision reflects the write: the writer immediately reads `stateHeadOffset`, or branch-local `getStateLen` on a handle without offsets, and another reader uses the changed revision to detect the append. (2 calling functions)
- `appendManyToStateJsonWithIdentity.7` — **pinned** — A retained append is readable as the same stamped items at the same positions through `getStateJson` and, when supported, `getStateSlice`. This lets another manager see the write and lets a reopened manager reconstruct the writer's window without its in-memory cache. (2 calling functions)
- `appendManyToStateJsonWithIdentity.8` — **pinned** — A batch can contain different object shapes without losing their fields: presentations retain `id`, tombstones retain `retract` and optional `undone: true`, and the header retains `v`. The write-down can supply all rows of the window and the header in one array. (1 calling function)
- `appendManyToStateJsonWithIdentity.9` — **pinned** — It accepts a one-item array as well as a multi-item array: the reload benchmark's last chunk can contain just one item. (1 calling function)
- `appendManyToStateJsonWithIdentity.10` — **pinned** — On success the answer has a `record` whose `sequence` and `id` equal the `at` and `by` actually stored on the items. The writer builds its in-memory index from that record and the input items without reading the stamps back. (1 calling function)
- `appendManyToStateJsonWithIdentity.11` — **pinned** — The answer's numeric `firstOrdinal` is the actual zero-based position the first item took in the target state: its item length immediately before this append, including intervening writes by another handle. The writer compares it with its cached length to decide whether it can extend that cache or must discard it. (1 calling function)
- `appendManyToStateJsonWithIdentity.12` — **pinned** — The record ID is stable and unique to the write across branches: an inherited record keeps its ID, but an independent presentation does not reuse it even at the same ordinal and sequence. The index compares `by` to recognize a shared prefix and to distinguish which presentation a removal concerns. (1 calling function)
- `appendManyToStateJsonWithIdentity.13` — **pinned** — The batch sequence is a usable branch point in the same history as the rows being presented. A branch or derive cut at that write includes the entire batch; a cut before it excludes the entire batch, never splitting a presentation or a body's shards. (1 calling function)
- `appendManyToStateJsonWithIdentity.14` — **pinned** — The store keeps or loses the append whole, and a refused append writes none of its items. This guarantee is per batch: refusing a retraction does not undo a separate write-down that already landed. (1 calling function)
- `appendManyToStateJsonWithIdentity.15` — **pinned** — Failure is signaled by a synchronous throw, not a normal error-valued answer; the caller needs no particular error code or message. A throw is not proof the write was refused: the index discards its cache and uses the next successful read on that branch to settle whether the batch landed, treating the outcome as unknown while the read also fails. (1 calling function)
- `appendManyToStateJsonWithIdentity.16` — **pinned** — A batch's published state-delta operation retains the `AppendMany` variant and an ordered array of item byte arrays, so a subscriber can replay all its items. (found in a test of the store)

## `appendToStateJson`

- `appendToStateJson.1` — **pinned** — Accept a string state ID and a caller-built JavaScript item directly, including nested objects, arrays and optional properties; callers do not encode the item as bytes. A freshly registered `append_log` must accept its first item without a separate write of `[]`. (11 calling functions)
- `appendToStateJson.2` — **pinned** — Add exactly one item at the end of the named state, leaving the earlier items in order. Live reads and reconstruction after reopening must expose the caller's JSON items, not record envelopes: readers use their fields, including caller-assigned IDs, and replay changes oldest first. (11 calling functions)
- `appendToStateJson.3` — **pinned** — Finish the state update synchronously on success and signal a write failure by throwing in the call. A delayed rejection, error return or silent no-op cannot drive the callers' retry, rollback or reporting paths; no caller examines the successful return value. (11 calling functions)
- `appendToStateJson.4` — **pinned** — The appended item's zero-based position is the previous array length, and an append does not renumber earlier items. Array positions must agree with length, point reads, edits and redactions wherever those APIs are used; the inference and process query APIs likewise use array position, not Chronicle record sequence, as their public sequence. (7 calling functions)
- `appendToStateJson.5` — **pinned** — An append must target the branch selected by the store handle, including a derived context's branch view. Code that switches or reopens a branch needs that branch's log history, not an unconditionally global append or an append to the trunk. (6 calling functions)
- `appendToStateJson.6` — **pinned** — Write an incremental append operation recognized by the registered snapshot strategy. The ordinary record must be proportional to the new item, not to the accumulated history; the coalescing journal puts its snapshot cadence beyond its expected length so that its own table writes handle compaction. (4 calling functions)
- `appendToStateJson.7` — **pinned** — Preserve inline JSON and caller-supplied blob references as distinct forms of the item. The context log resolves its stored `blob_ref` blocks, and inference, process and guard-audit readers recognize `{ blobId }` and fetch that exact blob later; append itself need not store or expand a blob. (4 calling functions)
- `appendToStateJson.8` — **pinned** — For writers that publish a corresponding in-memory projection only after the append, a refused append must leave no new item to replay. Otherwise the channel decision or label history disagrees with memory, or a context entry exists without its source index being updated. (3 calling functions)
- `appendToStateJson.9` — **pinned** — The context and autobiographical logs need readable JSON when a JavaScript string value contains a lone UTF-16 surrogate: it reads back as U+FFFD. Their byte-based edits deliberately match the object append for string values, and the strategy compares its in-memory mirror against that normalized stored form. (3 calling functions)
- `appendToStateJson.10` — **pinned** — Append must extend the current array even after `setStateJson` replaces it, without resurrecting the old items. The journal is explicitly emptied between checkpoints, and the strategy replaces repaired summaries and chunk records before it resumes appending. (3 calling functions)
- `appendToStateJson.11` — **pinned** — A successful append is an independent update ordered before later writes: failure or interruption of a subsequent write must not silently undo the earlier append. Recovery can see a merged summary before all its source edits, an ended record before the registry snapshot, or journal changes whose table compaction failed. (3 calling functions)
- `appendToStateJson.12` — **pinned** — Where `stateHeadOffset` is available, each successful summary or chunk append must change that state's revision on the branch by the time the call returns. Another strategy instance sharing the store uses an unchanged revision as proof that it can skip reading the state. (2 calling functions)
- `appendToStateJson.13` — **not met** — A successful later `sync()` must cover the preceding appends and make them recoverable after a crash. The guard does not submit original results before that barrier, and the coalescer does not acknowledge acceptance or start a render before its commit barrier. (2 calling functions) Not met: When Chronicle creates the store directory, sync returns without syncing its entry in the parent directory, so a machine crash can leave even the synced appends unreachable.
- `appendToStateJson.14` — **pinned** — An append to the ended-agent log must enter the suffix returned by `getStateTail`. When the recovery file is absent, boot decodes that suffix as a JSON array of the newest ended records in oldest-first order. (1 calling function)
- `appendToStateJson.15` — **pinned** — Keep the coalescer's own `seq` on each journal item unchanged. The next table stores the last such number, and restore applies only items above it, in log order; the record's store-assigned sequence is no substitute for this watermark. (1 calling function)
- `appendToStateJson.16` — **pinned** — The append operation published in a state delta keeps the `Append` variant name and carries the item's bytes as an array of integers, independently of how the record is encoded on disk. (found in a test of the store)

## `appendToStateJsonWithIdentity`

- `appendToStateJsonWithIdentity.1` — **pinned** — The write goes to the named append-log state on the receiver’s branch and survives a reopen. The state name is not fixed: callers use a shared or namespaced message slot, a namespaced window, and a namespaced quarantine ledger. (4 calling functions)
- `appendToStateJsonWithIdentity.2` — **pinned** — Each successful call adds exactly one JSON item at the old state length, including ordinal zero for an empty log. Prior items keep their order and ordinals; subsequent length and state reads see the addition. (4 calling functions)
- `appendToStateJsonWithIdentity.3` — **pinned** — The method accepts the item as a JavaScript object and preserves its JSON data alongside the stamps. That includes message content with blob references and optional shard metadata, a window item’s row id, tombstone or header, and a quarantine event’s nested records, outcomes or checkpoint entries. (4 calling functions)
- `appendToStateJsonWithIdentity.4` — **pinned** — The third and fourth arguments name the top-level fields to fill in the stored item, respectively with the writing record’s id and sequence. Messages use `id`/`sequence`, window writes use `by`/`at` so a presentation’s existing `id` still names the row, and quarantine writes use `eventId`/`sequence`. (4 calling functions)
- `appendToStateJsonWithIdentity.5` — **pinned** — Assigning the identity and appending the stamped item is one atomic record write. Another writer cannot take the reserved identity, and there is no intermediate record containing an unstamped item or a second record needed to complete it. (4 calling functions)
- `appendToStateJsonWithIdentity.6` — **pinned** — Success synchronously returns the writing record itself, with a string `.id` and numeric `.sequence` equal to the two stored stamps. Callers use those properties without a reread or `await`; the benchmark forwards the last such record as the `record` of its simulated batch. (4 calling functions)
- `appendToStateJsonWithIdentity.7` — **pinned** — A record id is stable and distinct from other append records’ ids. In particular, inherited window records keep their `by` stamp on a fork, but independent writes on divergent branches do not acquire the same stamp even at the same ordinal or sequence. (4 calling functions)
- `appendToStateJsonWithIdentity.8` — **pinned** — A refused append throws synchronously and writes nothing; it does not return a success-looking record or an error sentinel. The callers propagate the failure rather than applying a fictitious window item, announcing a message, marking an exhaustion written, or continuing the benchmark loop as if the write succeeded. (4 calling functions)
- `appendToStateJsonWithIdentity.9` — **pinned** — The stamped sequence is a position in the branch’s record history, not an item ordinal: a cut at it includes the complete write and a cut before it does not. Thus a later single-row presentation has a later cut point than the stored message it presents. (2 calling functions)
- `appendToStateJsonWithIdentity.10` — **pinned** — Where `stateHeadOffset` is available, a landed append changes the target state’s revision on that branch, as seen by every handle reading that branch. Message and window caches use the post-write revision to distinguish the new state from the old one. (2 calling functions)
- `appendToStateJsonWithIdentity.11` — **pinned partly** — A throw during or after a write is not proof that nothing landed. Once the same branch can be read, its state must reveal either no new item or the complete stamped item: message recovery checks the pre-append ordinal and body group, and window recovery discards its cache and reloads the index. (2 calling functions)
- `appendToStateJsonWithIdentity.12` — **pinned** — A single-item write does not by itself upgrade a version-1 store to MANIFEST version 2. WindowIndex deliberately uses the single form rather than passing a one-element batch. (1 calling function)
- `appendToStateJsonWithIdentity.13` — **pinned** — The newly appended message is readable at the tail in the same stored JSON form by point lookup and by full reconstruction. Optional `undefined` properties and lone surrogate halves must not make the message unreadable or give the warm cache a different serialized shape from a cold read. (1 calling function)
- `appendToStateJsonWithIdentity.14` — **pinned** — On a message slot with native history indexes, an append must not leave a queryable but stale index. A subsequent timestamp or channel query must find a matching appended ordinal, or the index must report that it is unavailable so MessageStore can re-register and retry. (1 calling function)
- `appendToStateJsonWithIdentity.15` — **pinned** — A quarantine event’s `eventId` is a nonempty string usable as an exact reference in a later ledger append. An alert or clear must match the intended exhaustion generation, and an `alert_sent` must still be able to name the pending event it acknowledges after replay. (1 calling function)
- `appendToStateJsonWithIdentity.16` — **pinned** — A successful ledger append precedes the side effect that relies on it. The pending-alert event must be persisted before external delivery, and the appended checkpoint at the old ledger length must survive redaction of the preceding items and subsequent compaction. (1 calling function)
- `appendToStateJsonWithIdentity.17` — **pinned** — For the benchmark’s per-row replacement for `appendManyToStateJsonWithIdentity`, successive single appends must leave the same window items, ordinals and presented rows as the batch, including after reopen. The deliberate difference is that each item names its own writing record instead of all items naming one record. (1 calling function)
- `appendToStateJsonWithIdentity.18` — **pinned** — When message appends trigger a full snapshot, its encoding adds little overhead to the serialized history instead of expanding every payload byte into a decimal integer. (found in a test of the store)
- `appendToStateJsonWithIdentity.19` — **pinned** — Repeated single-item identity appends keep disk growth near-linear in the bytes of the stamped items, including automatic snapshot overhead on a growing append log. (found in a test of the store)

## `catchUpSubscription`

- `catchUpSubscription.1` — **pinned** — One call with the string ID just returned by `subscribe(config)` must act on that subscription in place. The server does not await or use a return value; it returns the original ID and uses it for polling and unsubscribe. (1 calling function)
- `catchUpSubscription.2` — **pinned** — When `subscribe` was given a `fromSequence`, catch-up must replay history starting from that configured sequence. Zero selects catch-up too: the caller checks for `undefined`, not truthiness. (1 calling function)
- `catchUpSubscription.3` — **not met** — Replay must respect the subscription’s configured filter and limits on buffered events and snapshot size. The server supplies those settings to `subscribe`, not to `catchUpSubscription`, and forwards polled events without applying them again. (1 calling function) Not met: Catch-up replays records and states from the calling handle’s branch instead of the branch named in the filter, and a replayed array can exceed the snapshot byte limit because the store does not count its brackets and commas.
- `catchUpSubscription.4` — **pinned** — When `fromSequence` is absent, the same call must mark the subscription caught up immediately, without replaying history. It is a live-only subscription, not a request to start at sequence zero. (1 calling function)
- `catchUpSubscription.5` — **pinned** — The store must signal completion with a pollable `caught_up` event, even for live-only subscriptions. Like replay events, it needs JSON-parseable `data` and an unprefixed `eventType`: the server adds `store:` and the subscription ID itself. (1 calling function)
- `catchUpSubscription.6` — **pinned** — A catch-up failure that should fail the subscribe request must throw from the call; a returned error status or a later promise rejection is not checked. The request handler reports the exception’s message or string form and requires no particular error class or text. (1 calling function)

## `close`

- `close.1` — **pinned** — The caller can close the receiver with no arguments and no await. Closing must finish in that call; nobody uses a success return value, and some callers immediately exit the process. (17 calling functions)
- `close.2` — **pinned** — A successful close relinquishes the open store, including its path lock. Another open of the same path can proceed without waiting for the old process to exit or its JavaScript references to be collected; failed-start retries and repair verification rely on this. (17 calling functions)
- `close.3` — **pinned** — A close failure is a synchronous throw carrying the store's error, not a false result or a later promise rejection. Callers can propagate or aggregate that error, log it without undoing a completed write, fold it into an audit verdict, or deliberately suppress it in favor of the original open error. (17 calling functions)
- `close.4` — **pinned** — On successful close, previously completed writes survive for the next open, including state edits, branch changes, imported messages and load-time repairs. The caller does not need a separate successful sync before close for those changes to persist. (15 calling functions)
- `close.5` — **pinned** — Closing after inspection or a dry run must not itself change the logical application data merely read, or apply changes that the caller only planned. This is not a requirement to preserve the backing files byte for byte. (8 calling functions)
- `close.6` — **pinned** — Once the store itself has opened, it must be closable even if initialization of the framework, manager or strategy using it never completed. Successful higher-level teardown is not a prerequisite for releasing a failed creation. (7 calling functions)
- `close.7` — **pinned** — isClosed() must remain callable and accurately report whether close consumed the handle, including immediately after a throw. That lets callers skip a duplicate close or a read on a closed store, and lets framework shutdown distinguish retryable cleanup from a terminal failure. (5 calling functions)
- `close.8` — **pinned** — For failure of close's own final sync specifically, ContextManager promises that the store is closed all the same, whether close runs directly or at the end of an interrupted write. Framework shutdown also handles that consumed-on-error outcome; the throw is not evidence that the original handle can be retried. (3 calling functions)
- `close.9` — **pinned** — Closing an owned handle ends its use for live store reads, even though the manager still holds the JavaScript object. In particular, inspection of messages, branches and receipts through that manager is no longer available on that handle. (2 calling functions)
- `close.10` — **pinned** — The verification reread and the Claude import need a thrown failure with a useful .message for their operator-facing diagnostics. Neither matches a particular close-error code or literal message. (2 calling functions)
- `close.12` — **pinned** — Close remains a distinct operation after an explicit sync attempt: framework shutdown still calls it if that sync threw, and must be able to retain a close error alongside the earlier sync error. (1 calling function)

## `compactState`

- `compactState.1` — **pinned** — A single string state ID suffices to compact an existing `append_log` state. The IDs used are `messages` and the strategy’s namespaced quarantine-event ledger ID. (2 calling functions)
- `compactState.2` — **pinned** — Compaction takes effect by the time the call returns, without an `await` or any action on a returned record. The benchmark ends its build timer on the next line; the strategy exits its branch-scoped mutation lock without waiting for further work. (2 calling functions)
- `compactState.3` — **pinned** — The compacted state remains appendable under the same ID, with later items following the retained history. The benchmark appends and reads on both child and parent; the strategy continues appending quarantine events to be replayed after the checkpoint. (2 calling functions)
- `compactState.4` — **pinned** — Explicit compaction works on messages already appended while automatic snapshots were disabled. Re-enabling snapshots does not have to be followed by another append before compaction can run. (1 calling function)
- `compactState.5` — **pinned** — Compaction leaves the full message history readable as the same ordered array, both via `getStateJson('messages')` on the parent and on branches derived from its compacted head. The benchmark rejects a child that does not inherit exactly `size` messages. (1 calling function)
- `compactState.6` — **pinned** — The strategy’s compaction acts on the ledger of the branch current on its store handle, not on a same-named state on another branch. It supplies no branch argument and checks the captured branch name and generation immediately before the call. (1 calling function)
- `compactState.7` — **pinned** — After the caller appends a checkpoint and redacts the preceding event range, compaction leaves a short logical ledger: the redacted prefix no longer counts toward `getStateLen` or reappears in the event array. The caller uses that length to decide when another checkpoint is due. (1 calling function)
- `compactState.8` — **pinned** — Compaction preserves the surviving checkpoint as the complete replayable quarantine projection, including generation IDs and alert bookkeeping. Interruption at compaction must not leave a reader without that checkpoint: even an empty checkpoint supersedes records in the legacy snapshot. (1 calling function)

## `createBranchAt`

- `treeSet.5` — **pinned** — Report a failed operation by throwing in the call, not by returning a sentinel or later rejecting a promise. - `treeSet.6` — **pinned** — Record the set in the branch selected by the supplied store or view, with the tree version belonging to that point in branch history, not as a global latest value.
